# AGENTS.md: technical notes for working on this project

User-facing setup is in README.md. This file covers how the firmware works,
how it is verified, and what to watch out for.

## Working rules

- **Verify before touching hardware.** Every change goes through the host
  tests (`tools/run_tests.sh`, with `GUTENPRINT=1 AIRPRINT=1` for printing or
  IPP changes) and, when firmware behaviour changes, the QEMU self test.
- **Flash only with the user's go-ahead.** That includes OTA updates
  (`pio run -t ota`, `tools/remote.py upload`), rebooting it and the `panic`
  test. Reading the serial log, `/info` and the remote log of a running
  board is fine.
- **Never read or print the secrets** in `.env` or the generated
  `src/local_config.h`. To check whether a key is set, test for a non-empty
  value without printing it, e.g. `grep -qE '^WIFI_SSID=.+' .env`.
- **Keep the printing core portable.** `components/canon_bjl`,
  `components/airprint` and `components/scanner` build both natively
  (`host/`) and for the ESP32. Platform specifics go behind hooks or
  `#ifdef ESP_PLATFORM`.
- **Optimisations must not change output.** Pure speed changes must keep the
  reference CRCs below unchanged.

## Configuration

- `.env.example` (committed) lists every key with its default. `.env`
  (git-ignored) overrides them, and is created from the example on the first
  build. Every key becomes `#define KEY "value"` in `src/local_config.h`.
  Keys: `WIFI_SSID`, `WIFI_PASSWORD`, `PRINTER_NAME`, `HOSTNAME`,
  `MODE` (`normal` | `debug` | `dev`).
- `sdkconfig.defaults` holds all ESP-IDF settings; the qemu env adds
  `sdkconfig.defaults.qemu` (DIO flash, see Gotchas). The generated
  `sdkconfig.<env>` is git-ignored; delete it to pick up changed defaults.
- `PROJECT_VER` is set in `CMakeLists.txt`, because ESP-IDF's `git describe`
  fails in a repository without commits.

## Build and test

```
pio run -e esp32s3                  # firmware
pio run -e esp32s3 -t upload        # flash (only with the user's go-ahead)
tools/run_tests.sh                  # unit tests, test pages, scans, firmware build
GUTENPRINT=1 AIRPRINT=1 tools/run_tests.sh   # + Gutenprint equivalence + AirPrint and scanning on the Mac
QEMU_XTENSA=/path/qemu-system-xtensa QEMU_LIB_PATH=... tools/qemu_selftest.sh
```

QEMU builds are at https://github.com/espressif/qemu/releases. Older macOS
arm64 builds need Homebrew's `libslirp`: fetch its bottle with
`brew fetch libslirp`, unpack it anywhere, and pass that lib dir plus
`/opt/homebrew/lib` in `QEMU_LIB_PATH`. `esp-develop-9.2.2-20260417` only
needs `/opt/homebrew/lib` (pixman, libgcrypt, SDL2). macOS strips `DYLD_*`
variables before they reach scripts, so the script sets them itself.

To try the scan page on the Mac: `cd host && ./airprint_host`, then open
http://localhost:8631/scan (`FAKE_SCANNER_KBPS`, `SCAN_BUF_KB` to vary the
emulated USB rate and the buffer size).

## Printer protocol (MG2500 series)

- USB ID `04a9:176d`, printer interface 1 (bidirectional, bulk OUT `0x01`,
  bulk IN `0x82`). Its IEEE 1284 ID starts
  `CMD:BJL,BJRaster3,BSCCe,IVEC,IVECPLI;MDL:MG2500 series`.
- It has no page description language: it takes Canon BJ raster commands
  wrapped in IVEC XML. Sources: Gutenprint 5.3.5 `print-canon.c` (the MG2500
  series is the "PIXMA MG2400" model there, model 8002400) and Canon's
  cnijfilter 4.00 (model 423), which uses the same IVEC operations.
- Job: `StartJob` XML, `ModeShift` XML. Then per page: `ESC [K` reset (first
  page only), page setup (`ESC (b (q (d (t (c (p (P (T (l (v`), multiraster
  mode (`ESC (I`, `(J` 8 lines per block, `(L` "CMYK"), and `ESC (F` blocks
  of PackBits lines, each line terminated by `0x80`, one block per ink per 8
  lines. A page ends with FF and `ESC (b 0`. The job ends with `ESC @` and
  the `EndJob` XML.
- Modes (Gutenprint's MG2400 table):
  - `600x600dpi`: C/M 2 bits per pixel with 3 levels, Y/K 1 bit
  - `300x300dpi`: CMYK all 1 bit
- Paper: A4 (`ESC (P` size `0x03`, 4961×7016 in 1/600") and Letter (`0x0d`,
  5100×6600). Borders are 10/10/9/15 pt (left/right/top/bottom).
- Our streams are byte-identical to Gutenprint's, except Gutenprint drops a
  page's last 8 lines when the height is a multiple of 8
  (`canon_write_multiraster` never flushes that block).
- Back channel: when read, the printer answers with about 1 KB of
  `GetStatusResponse` XML (status, `status_detail` such as
  `MarkerSupplyAttention`, Canon fields such as `CIR:CL=000,BK=UK` for ink).
  Poll it at most every 2 s when idle and every 250 ms during a job, and
  reassemble replies from the 512-byte reads. Like Canon's driver, we wait up
  to 5 s for the `StartJob`/`ModeShift` replies and up to 180 s for
  `EndJob` (the page is done), and carry on if a reply never comes.
- Cancel: stop at a line boundary, finish the page (eject) and end the job.
  If the printer stops accepting data, after 8 s abort the transfer and send
  the printer-class SOFT_RESET.

## Scanner protocol (MG2500 series)

- Source: SANE's pixma backend, `backend/pixma/pixma_mp150.c`. The MG2500
  (`MG2500_PID 0x176d`) is a "generation 5" flatbed there: CIS sensor, up to
  600 dpi, 638 x 877 units of 1/75 in, no ADF. SANE uses USB interface 0
  (vendor class); we pick the vendor interface with bulk IN + OUT that is not
  the printer interface.
- Command: u16be code, zeros, u32be payload length (+ expected reply data) at
  offset 12, payload whose last byte makes its sum 0. Reply: u16be status
  (`0x0606` ok, `0x1414` busy, `0x1515` failed), 6 zeros, data with the same
  checksum. XML commands are sent raw on the same endpoints.
- Scan: XML `StartJob` + `ModeShift` (servicetype `scan`), start session
  `0xdb20` (retry 10 x 1 s while busy), gamma table `0xee20` three times
  (1024 x u16le, gamma 2.2), parameters `0xd820` (0x38 bytes: dpi `|0x8000`,
  x rounded down to 32, raw width rounded up to 32, height, colour `0x08`/24
  bpp, calibrate flag), start `0xd920`, poll status `0xda20` until byte 0 bit
  0/1 (calibrated), wait 1 s, read image `0xd420` blocks until flags & 0x28 ==
  0x28, then abort session `0xef20` and XML `EndJob`. The last two are sent
  on every exit path: otherwise the scanner reports `PCScanning` and may need
  a power cycle.
- Image blocks: 16-byte header (flags at 8, u32be length at 12) + raw 8-bit
  RGB lines of the padded width; a block of length 0 means "not ready yet"
  (SANE sleeps 10 ms). We ask for 512 KB blocks like SANE and read them in
  8 KB transfers, so nothing block-sized is held.
- Timeouts as SANE: 1 s per transfer, 8 tries for a reply, 120 s for the
  calibration. We calibrate on every scan (what `scanimage` does).
- USB details we handle without knowing what the MG2500 does: zero-length
  packets after replies that are a multiple of 64 bytes are skipped, and IN
  transfers are rounded up to the max packet size (an ESP-IDF requirement).
- Nothing of this has run on the real scanner yet. The descriptor dump at
  attach (`interface N: class ...`) shows the interfaces on the first boot.

## Scanning

- Pipeline: scanner lines -> crop -> `jpeg_enc` (one 16-line strip in memory,
  YCbCr 4:2:0, quality 85, JFIF dpi) -> shared buffer -> HTTP. Colour only.
- Shared buffer (`shared_buf.c`): all PSRAM but 512 KB, allocated at boot
  (about 7.5 MB). Scans and the dev mode print capture take turns; whoever
  wrote it last owns the content until the next user takes it.
- Stream mode (`GET /scan/stream.jpg?dpi=150|300|600&paper=a4|letter`): the
  buffer is a ring between the scan thread and the connection. Usually the
  whole JPEG fits (300 dpi A4: a few hundred KB to a few MB). A client that
  falls behind pauses the scan, one that stops reading for 60 s cancels it,
  and a client that disconnects cancels it at once. A stream always ends
  with a complete JPEG (missing lines white).
- Last mode (`POST /scan/last?paper=...`): 150 dpi, kept whole in the buffer
  for `GET /scan/last.jpg` until the next user of the buffer. A JPEG that
  does not fit fails the scan.
- `GET /scan/status` (JSON) drives the page; `POST /scan/cancel` stops at the
  next block. One scan at a time (409); a scan holds the device like a print
  job, so print jobs get `server-error-busy` and scans 503 while printing.
  The printer's status polling pauses during a scan.
- The page (`scan_page.h`) reads the stream with `fetch()` and redraws the
  partial JPEG from a Blob every 1.5 s; Save downloads the Blob.
- eSCL / AirScan under `/eSCL` (same server, ports 80 and 631; mDNS
  `_uscan._tcp` on port 80, `rs=eSCL`, the printer's UUID, and `Scan=T` in
  the IPP record). Capabilities: platen 2552 x 3508 (1/300 in), RGB24,
  JPEG, discrete 75/150/300/600 dpi. `POST ScanJobs` parses the settings
  (region in 1/300 in, the lowest native dpi at least the requested one),
  answers 201 + `Location: /eSCL/ScanJobs/<id>`; the scan only starts at
  `NextDocument`, which streams the JPEG chunked (as AirSane does); the next
  `NextDocument` is 404. `DELETE` cancels; jobs are kept in a ring of 4 for
  `ScannerStatus`.
- macOS (Image Capture, AirScanScanner 63.2 on macOS 26) seen on hardware:
  capabilities, icon, `ScannerStatus` every 3 s, then `POST ScanJobs` with
  `TextAndGraphic`, A4 region, `image/jpeg`, RGB24, then `NextDocument`, and
  `DELETE` of the finished job. Canceling in Image Capture sends `DELETE`
  mid-stream. A scripted ImageCaptureCore client never got as far as `POST`
  (the driver polls status forever): test with Image Capture itself.
- Tests: `scan_host selftest` runs the protocol against `fake_scanner`
  (busy, cancel, scanner errors, odd areas, pixel-exact lines; the fake flags
  any protocol violation, unread reply or unclosed session), JPEGs are
  decoded and compared (PSNR 40-47 dB on the test page, limited by 4:2:0),
  and the HTTP flows run against `airprint_host` and in QEMU. QEMU has no
  PSRAM, so its buffer is 48 KB of internal RAM (more starves the network in
  the 600 dpi print test): streamed JPEGs must be byte-identical to the host
  build's, and a kept scan must fail cleanly. The scan thread uses about
  3 KB of its 8 KB stack.

## AirPrint / IPP

- One server, two ports: 631 for IPP (and the pages), 80 for browsers
  (`web_port`; the mDNS `adminurl` points there). Port 80 also accepts IPP.

- mDNS: `_ipp._tcp` on port 631 with the `_universal` subtype (needed by iOS)
  and `_print` (IPP Everywhere). The TXT record follows Bonjour Printing,
  with `URF=V1.4,CP1,W8,SRGB24,RS300-600,MT1,PQ3-4-5` and `air=none`.
- Operations: Print-Job, Validate-Job, Create-Job, Send-Document, Cancel-Job,
  Cancel-My-Jobs, Close-Job, Get-Job-Attributes, Get-Jobs,
  Get-Printer-Attributes, Identify-Printer (flashes the LED blue).
- Formats: `image/urf` and `image/pwg-raster` (8-bit sRGB or sgray, 300/600
  dpi, sniffed for `application/octet-stream`). The page's dpi picks the
  printer mode, and its height picks the paper (under 11.35 in means Letter).
- Pipeline: socket -> raster decoder (one line at a time) -> `bjl_render`
  (crop to the printable area, sRGB -> CMYK with full black generation
  `C = (c-k)/(1-k)`, dot gain curve, ordered dither) -> `canon_bjl` ->
  `job_write` hook. One job at a time; a second one gets `server-error-busy`.
- iOS flow seen on hardware: Validate-Job, Create-Job, then Send-Document
  with URF at 600 dpi colour. No IPPS was needed.
- HTTP: keep-alive, chunked bodies, `Expect: 100-continue`. Unread document
  data is always drained before replying: closing early resets the
  connection, the client loses the response, and libcups retries the whole
  job.
- iOS keeps several keep-alive connections open while it watches a job, so
  the limit is 8 connections with a 15 s idle timeout. Refusals are logged.
- Status mapping: `MarkerSupplyAttention` becomes `marker-supply-low-warning`.
  The `CIR` field gives ink levels (`UK` means unknown). The port status
  "paper empty" bit becomes `media-empty-error`. The names used for jam and
  cover open are guesses (never seen on hardware).
- Conformance (ipptool): IPP 1.1 and 2.0 pass everything, and IPP Everywhere
  passes all but `image/jpeg`. Results are the same on the host, in QEMU and
  on the board.

## Debug mode (`MODE=debug`)

For a board left at the printer without a USB cable to a computer: normal
printing and scanning, plus (`src/debug.c`, driven by `tools/remote.py`):

- Log: `esp_log_set_vprintf` copies every line (cut at 255 chars) into a
  64 KB PSRAM ring: `GET :8080/log`, live on TCP 2323 (one client at a
  time). The last 3 KB also go to RTC memory (`RTC_NOINIT_ATTR`), which
  survives panics, watchdogs and software resets, and open the next boot's
  log. Not used: a PSRAM noinit segment (conflicts with
  `SPIRAM_IGNORE_NOTFOUND`, which QEMU needs).
- Crashes: ELF core dump to the `coredump` partition (128 KB); the next boot
  logs the crashed task and backtrace; `remote.py crash` downloads it and
  decodes it with `esp_coredump` and the build's `firmware.elf` (it must be
  the build that crashed). `POST /panic` crashes on purpose.
- OTA: `POST :8080/ota` with `firmware.bin` (checked: ESP32-S3 image of this
  project, validated by `esp_ota_end`), refused while printing or scanning.
  Rollback (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`): a new image stays
  "pending" until it has had WiFi and the debug server for 20 s
  (`debug_ota_confirm`, run in every mode so an image that switches mode is
  confirmed too); any reset before that, or 180 s without, brings back the
  previous image. `remote.py upload` waits for the reboot and the
  confirmation, and identifies builds by the ELF SHA-256 in the image.
- `/info`: version, ELF SHA, partition and OTA state, uptime, reset reason,
  heap, RSSI, core dump, task list with stack high-water marks.
- No authentication: anyone on the network can update the firmware. An image
  built with another MODE has no OTA: the next update needs USB.
- The bootloader (rollback) and the partition table (coredump) only change
  with a USB flash, never over OTA.

## Dev mode (`MODE=dev`)

`airprint_esp.c` swaps the printer hooks for a fake printer: always ready,
jobs converted and checksummed, the printer data kept in the shared buffer
(if it fits) and served at `GET /dev/last-job.prn`. Decode the download with
`tools/bjl_decode.py --png` (`http://<host>/dev/last-job.prn`). Scans come from `fake_scanner` at about USB
speed. The USB host still runs.

## Performance (ESP32-S3 @ 240 MHz)

- A4 page: 300 dpi about 2.2 s, 600 dpi about 8 s (text) or 9 s (photo).
  The MG2500 needs 7.5 s or more per page. Each job logs its time split
  (network / output / render / decode) and the CPU cycles per render stage.
- What mattered, in order:
  1. Pass white lines as `NULL` from the decoder and fill runs in bulk.
  2. A tight white-skipping loop, with the CMYK conversion `noinline`. At
     `-O2` GCC hoisted the conversion above the white test and spilled
     registers, costing about 50 cycles per white pixel.
  3. Skip dithering inks that have no coverage, skip all-zero groups of
     8 pixels, and dither only the inked span.
  4. `-O2` (ESP-IDF defaults to `-Og`), IRAM for hot functions (`BJL_HOT`),
     32 KB instruction / 64 KB data caches, QIO flash. Small gains each.
- Memory: per-line buffers come from internal RAM (`BJL_MALLOC_FAST`), and
  the Canon block buffers from PSRAM (`BJL_MALLOC_BULK`). The shared buffer
  takes the rest of the PSRAM. A scan adds 12 KB of USB transfers, about
  20 KB of protocol buffers and an 8 KB thread stack in internal RAM, and the
  encoder strip (60 KB at 300 dpi, 120 KB at 600 dpi) in PSRAM. The lowest free internal RAM seen during a 600 dpi
  job is about 67 KB. IPP connection threads have 12 KB stacks and use about
  3.5 KB.
- The conversion loop yields every 64 lines (`vTaskDelay(1)`). Without that,
  the task watchdog fires.

## Gotchas

- QEMU cannot emulate octal PSRAM; `CONFIG_SPIRAM_IGNORE_NOTFOUND=y` lets
  the firmware boot without it.
- QEMU does not emulate the quad I/O read command: with QIO, direct flash
  reads (`esp_partition_read`: OTA image check, core dump) return garbage
  while mmap reads work. The qemu env builds with DIO
  (`sdkconfig.defaults.qemu`); the board keeps QIO.
- Sockets: `CONFIG_LWIP_MAX_SOCKETS=24` covers IPP (8 connections + 2 listeners),
  mDNS, SNTP and the debug server (3 + listener + control) and log stream.
- PlatformIO's `board_build.flash_mode` only affects the uploader. QIO is
  set by `CONFIG_ESPTOOLPY_FLASHMODE_QIO` (the header still reads "dio",
  which is expected on the S3).
- The ESP-IDF WiFi driver logs the SSID at info level. Its log level is set
  to warn so the network name doesn't end up in logs.
- The app partition starts at `0x20000` (OTA layout, `partitions.csv`).
- USB-OTG VBUS: a spec-compliant printer only appears on the bus when 5 V is
  on VBUS, so the board's USB-OTG pads must be bridged.

## Limitations and ideas

- Plain paper only (no photo media, no borderless). A4/Letter only. No
  copies (clients repeat the pages), no duplex, no JPEG/PDF, no gzip, no
  IPPS, no authentication, IPv4 only. WiFi settings are compiled in.
- The colour tuning (dot gain 0.25 CMY / 0.15 K, full black generation) has
  not been checked on paper yet.
- Scanning: colour JPEG only. 150 dpi A4 takes 15 s on the board (about 6 s
  of warm-up and calibration); higher resolutions are limited by full-speed
  USB (about 0.5-1 MB/s of raw RGB: 300 dpi A4 is 26 MB). Paper comes out
  light grey (gamma 2.2, no white point correction).
- Ideas: buffer converted pages in PSRAM so clients can disconnect early;
  PDF output for eSCL (a JPEG wrapped in a one-page PDF); the scanner's own JPEG mode (SANE
  only uses it for ADF models: `0xd820` byte 3 = 1, byte 0x21 = 0x83); an SD
  card for large spools (pinout in `docs/sd_card_pinout.png`).
